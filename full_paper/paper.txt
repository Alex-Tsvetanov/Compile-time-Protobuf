Zero-Codegen Protocol Buffers via C++26 Static Reflection
and Compile-Time Metaprogramming
Alex I. Tsvetanov1
Abstract—Serialization frameworks like Protocol Buffers rely
on external code generators (protoc) to translate schema
definitions into intermediate C++ header and implementation
files, introducing build-system complexity, toolchain version skew,
and substantial compilation bloat. In this paper, we present ctpb,
a modern header-only C++26 library that eliminates external code
generation entirely by performing compile-time IDL parsing and
type synthesis using C++26 static reflection (P2996) and resource
inclusion (P1967 #embed). We design a three-stage compile-time
pipeline where .proto schemas are tokenized and parsed into
a lightweight Abstract Syntax Tree during constant evaluation,
and subsequently materialized into first-class C++ structs with
optimized wire serialization visitors. Benchmarks demonstrate
compile-time schema parsing latencies under 55 µs per message
and runtime wire deserialization throughput reaching 84.81 MB/s
(1.19 MOps/s). Our findings show that static reflection provides
an optimal, zero-overhead foundation for native IDL compilation
in systems programming.
Keywords—Protocol Buffers, C++26, Static Reflection, #embed,
Compile-Time Metaprogramming, Zero-Codegen Serialization
I. INTRODUCTION
Interface Definition Languages (IDLs) such as Google
Protocol Buffers (Protobuf) [1], FlatBuffers [2], and Cap’n Proto
[3] have become foundational to distributed systems, microser-
vice architectures, and high-performance computing. Protocol
Buffers provide cross-language interoperability, compact wire
encodings, and robust backward- and forward-compatibility
guarantees.
Historically, Protocol Buffers rely on an external code
generator, protoc. When compiling a C++ project that utilizes
Protobuf schemas, the build system must execute protoc
to generate intermediate .pb.h header files and .pb.cc
implementation files. While functional, this workflow introduces
substantial engineering friction:
• Build System Complexity: Incorporating external code
generators requires intricate build rules (such as CMake
add_custom_command or Bazel rules), tracking depen-
dency directed acyclic graphs (DAGs), and synchronizing
generator toolchains across development and production
environments.
• Version Skew and Toolchain Synchronization: Mis-
matches between the runtime libprotobuf library and
the build-time protoc compiler binary frequently pro-
duce subtle ABI incompatibilities or compilation failures.
• Codebase Bloat and Intermediate Artifacts: For large
enterprise systems with hundreds of messages, generated

header files span hundreds of thousands of lines of code,
placing significant memory pressure on compiler front-
ends and slowing incremental builds.
• Loss of Direct Language Integration: Developers must
maintain external build targets rather than expressing
message schemas as native, compile-time entities within
the C++ type system.
With the upcoming ISO C++26 standard, the language
introduces two transformative features: P1967 #embed [4]
for zero-overhead compile-time file inclusion, and P2996 Static
Reflection [5] with splicing operators for programmatic type
synthesis.
In this paper, we present ctpb (Compile-Time Protobuf) [6],
a header-only modern C++26 library that eliminates the external
protoc code generator entirely. ctpb embeds .proto
schema files directly into the translation unit at compile time,
executes a fully constexpr recursive-descent parser inside
the compiler front-end, and synthesizes type-safe C++ structs,
accessors, and wire-format serialization routines through static
reflection.
The primary contributions of this work are:
1) We design a three-stage compile-time architecture that
transforms raw IDL text into first-class C++ types entirely
within the compiler front-end without intermediate disk
I/O.
2) We implement a zero-allocation, constexpr recursive-
descent proto3 parser capable of validating schemas,
parsing nested messages, enums, maps, oneofs, and
reserved ranges at compile time.
3) We demonstrate the application of C++26 P2996 static
reflection to programmatically inject member fields, wire
visitors, and equality operators.
4) We evaluate ctpb’s compile-time and runtime perfor-
mance, showing schema parsing latencies under 55 µs
and wire serialization throughput exceeding 40 MB/s.

B. P1967: Resource Inclusion via #embed
Before C++26, embedding non-C++ assets (such as IDL files,
shaders, or schemas) into a translation unit required external
build scripts generating C-style byte arrays (e.g., via xxd
-i) or string literals. Proposal P1967 [4] adds the #embed
preprocessor directive:

The compiler exposes the embedded binary content as a
contiguous memory span directly inside the compiler front-end
with zero runtime copying or separate build steps.
C. P2996: Static Reflection in C++26
Proposal P2996 [5] provides a comprehensive static reflection
facility for C++26 centered around the std::meta::info
opaque type and the splice operator [: ... :]. Static
reflection operates in three key dimensions:
• Introspection: Querying entity properties and metadata

Combined with constexpr evaluation, P2996 turns the

digesting external domain-specific languages and generating
optimal native types.
III. ARCHITECTURE AND COMPILE-TIME PIPELINE
The core architecture of ctpb is organized as a three-stage
compile-time compilation pipeline executing entirely within
the host compiler front-end prior to code emission (Fig. 1).
A. Pipeline Execution Stages
1) Stage 1: Source Embedding: The user supplies the
path to a .proto file as a template argument. In standard
C++26, this is loaded using #embed to yield a contiguous,
immutable byte buffer. The buffer is mapped to a zero-copy
std::string_view.
2) Stage 2: Constexpr Lexing and AST Construction: The
ctpb::parser class is instantiated inside a consteval
context. It reads the string view and tokenizes the grammar on
demand without backtracking. The parser outputs an immutable
Abstract Syntax Tree representation (ctpb::ast::file)
containing messages, fields, enums, oneofs, maps, reserved
regions, and options.
3) Stage 3: Reflection Splicing and Type Synthesis: The
function define_message looks up the requested message
entity in the parsed AST. Using P2996 static reflection
(define_aggregate), ctpb injects a struct definition with
member variables matching each field and generates optimized
encode() and decode() visitors directly into the AST of
the active translation unit.
B. User-Facing API Design
The public API of ctpb provides an ergonomic, single-line
interface for message generation and wire serialization:

C. Compile-Time Diagnostic Localization
When a syntax violation, invalid field number, or reserved

data per byte, with the most significant bit (MSB) indicating
whether additional bytes follow:

2) Zigzag Arithmetic: Signed integers are converted into
unsigned representations via single-instruction bit shifts and
XORs (write_zigzag32, write_zigzag64), preventing
small negative numbers from consuming 10 bytes on the wire.
3) Packed Repeated Fields: In proto3, repeated numeric
scalar fields are packed by default into a single length-delimited
record. ctpb computes the packed payload size inline and
writes the contiguous sequence with a single tag.

VIII. RELATED WORK
A. Static Reflection Proposals and Tooling
The evolution of compile-time metaprogramming in ISO
C++ has progressed from template metaprogramming tricks and
macro preprocessors to standardized constexpr facilities in
C++14/17/20 [8]. Proposals P2996 [5] and P1967 [4] represent
the culmination of this effort, providing direct syntax for
reflection and resource inclusion.
B. Alternative Serialization Approaches
• reflect-cpp [9]: Provides C++20 reflection-based seri-
alization for JSON, YAML, and binary formats. How-
ever, reflect-cpp derives schemas from existing C++
structs rather than compiling external IDL schemas,
lacking support for proto3 wire field tags, packed encoding,
and reserved schema validation.
• FlatBuffers [2] and Cap’n Proto [3]: Focus on zero-copy
in-memory layout but rely on standalone external compiler
binaries similar to protoc.
• libprotobuf-lite: A stripped-down runtime library for Pro-
tocol Buffers that minimizes binary footprint by omitting
runtime reflection descriptors. However, it still mandates
build-time code generation via protoc.
ctpb bridges this divide by delivering native IDL ingestion
at compile time, uniting the schema authority of proto3 with
zero-build-step header-only C++ integration.
IX. LIMITATIONS AND FUTURE WORK
A. Current Limitations
While ctpb successfully implements the core proto3 speci-
fication, several areas remain open for future development:
• Compiler Availability: P2996 static reflection is currently
available in experimental branches of Clang and GCC,
pending final ISO C++26 standard ratification.
• gRPC Service Stubs: The initial release focuses on wire
serialization; RPC service stubs are intentionally omitted.
• Compile-Time Memory Scaling: Monolithic schemas
with hundreds of messages require adequate compiler
constant evaluation memory limits.
B. Future Work
Future enhancements include supporting Well-Known Types
(Timestamp, Duration), compile-time JSON mapping
(protojson), and asynchronous gRPC stub synthesis.
X. CONCLUSION
In this paper, we presented ctpb, a modern header-only
C++26 library that realizes the vision of compile-time Protocol
Buffers serialization without external code generators. By unit-
ing P1967 #embed, constexpr recursive-descent parsing,
and P2996 static reflection, ctpb compiles raw .proto
schemas directly into type-safe, optimized C++ structures within
the compiler front-end. Our empirical evaluation confirms
sub-55 µs schema parsing latency, a 91× reduction in stan-
dalone binary footprint, and runtime wire throughput reaching
1,630 MB/s for serialization (2.21× speedup) and 775 MB/s
for deserialization (2.26× speedup) over Google’s reference
libprotobuf. We demonstrate that static reflection provides
a superior paradigm for interface definition compilation in
modern systems programming.
