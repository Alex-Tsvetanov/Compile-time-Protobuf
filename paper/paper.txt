Zero-Codegen Protocol Buffers via C++26 Static Reflection
and Compile-Time Metaprogramming
Alex I. Tsvetanov1
This paper presents ctpb (Compile-Time Protobuf) [6], a
header-only C++26 library that carries .proto schemas in the
translation unit as compile-time strings, runs a constexpr
recursive-descent parser in the compiler front-end, and synthesizes type-safe structs and wire-format routines through
static reflection. The contribution is a three-stage architecture
that turns raw IDL text into first-class C++ types without
generated intermediate files. Its parser handles nested messages,
enums, maps, oneofs, and reserved ranges, while P2996 injects
fields and makes wire visitors available programmatically. The
evaluation reports a 7.487 µs parse for a synthetic 100-field
schema and a 4.80× encoding speedup over libprotobuf
3.21.12 on a 47-byte Person workload, with bidirectional
wire-format tests against the reference implementation, and it
measures the build cost the removed generator is replaced by.

Abstract—Serialization frameworks such as Protocol Buffers
typically rely on external code generators (protoc) to translate
schemas into C++ files, which adds build rules, version coupling,
and generated source. This paper presents ctpb, a header-only
C++26 library that uses static reflection to parse .proto schemas
and synthesize C++ types during compilation. The library carries
the schema in the translation unit as a compile-time string,
performs a constexpr recursive-descent parse into an Abstract
Syntax Tree, and materializes type-safe fields and wire-format
visitors without generated .pb.h or .pb.cc files. On one host,
a synthetic 100-field schema is parsed in 7.487 µs (range 7.442
to 7.515 µs). For a 47-byte, three-field Person workload, ctpb
encodes 4.80× faster than libprotobuf 3.21.12, while decoding
leads by 1.26× to 1.46× and includes proto3 UTF-8 validation.
A stripped sample executable is 18,792 bytes versus 1,759,368
bytes for the generated-code static-runtime comparison. Removing
the generator relocates its cost into the front end rather than
eliminating it: the same schema at 100 fields builds 2.87× more
slowly than the generated path. Wire-format fidelity is verified
bidirectionally against the reference implementation.
Keywords—Protocol Buffers, C++26, Static Reflection, CompileTime Metaprogramming, Zero-Codegen Serialization

B. Recursive-Descent Parser
The proto3 grammar is formalized into approximately fifty
LL(1) productions, and the parser builds the structural AST in
a single pass without backtracking. Message parsing dispatches
on the leading token of each body element, recursing for nested
messages and delegating to dedicated productions for enums,
oneofs, maps, and reserved ranges; anything else is parsed as
a field declaration.

ctpb is organized as a three-stage pipeline executing entirely
within the compiler front-end prior to code emission.
Stage 1, source ingestion. The schema text is supplied as a
non-type template argument and held in immutable compiletime storage, mapped to a zero-copy std::string_view.
#embed is the standardized route from a .proto file to
that storage without a generated source file; the evaluated
implementation takes the text itself, so the file-reading step is
not exercised here.
Stage 2, constexpr lexing and AST construction. The
ctpb::parser is instantiated inside a consteval context,
tokenizing the grammar on demand without backtracking and
emitting an immutable AST (ctpb::ast::file) holding
messages, fields, enums, oneofs, maps, reserved regions, and
options.
Stage 3, reflection splicing and type synthesis.
define_message looks up the requested entity in the AST
and, via P2996 define_aggregate, injects a struct whose
members match each field directly into the active translation
unit. Generic ctpb::encode and ctpb::decode visitors
use the resulting metadata.

B. Type Mapping and Generated Interface
The synthesized members follow a fixed mapping: the sized
integer types map to the corresponding C++ integer types (with
sint and sfixed variants sharing the signed representation
and differing only in wire encoding), float/double/bool
map to their C++ equivalents, string to std::string,
bytes to std::vector<std::byte>, and repeated

T to std::vector<T>. The mapping is partial rather than
complete: map and oneof members are parsed into the AST
but are not yet synthesized, and a field whose type is an enum
or a nested message is emitted as int rather than as a distinct
type.
Beyond member generation, ctpb supplies direct dot-syntax
field access (p.name) and non-intrusive ctpb::encode and
ctpb::decode visitors that traverse the member descriptors
reflectively.
VI. W IRE F ORMAT E NGINE
A. Encoding
The serialization engine in ctpb::wire manipulates the
byte stream directly, without intermediate buffers. Encoding
proceeds in two passes: byte_size() computes the exact
wire length from compile-time field metadata, the output buffer
is allocated once, and the fields are then written through a
raw pointer with no reallocation or virtual dispatch. Varints
emit seven payload bits per byte with the high bit signalling
continuation; signed integers are Zigzag-converted with shifts
and XORs; and repeated numeric scalars, which proto3 packs
by default, have their payload size computed inline and are
written as one contiguous length-delimited record under a single
tag.
B. Deserialization and Error Recovery
The ctpb::wire::reader operates on a non-owning
std::span<const std::byte> and bounds-checks every read: varint decoding refuses to advance past the buffer end
or beyond the ten-byte maximum width, and length-delimited
reads validate the declared length against the remaining
bytes before yielding a subspan. ctpb::decode returns
failures as std::expected<T, decode_error> rather
than throwing, so decoding remains usable in noexcept
contexts.
Unknown field numbers are tolerated during decoding. The
skip_field method uses the wire type alone to advance past
an unrecognized integer, fixed-width block, or length-delimited
payload, allowing an older ctpb reader to consume a message
containing newer fields. Skipped fields are not retained for
re-serialization.

E. Wire Interoperability and Message Framing
Correctness was assessed through dual-direction interoperability tests against libprotobuf 3.21.12 and the
protoc code generator [1]. These tests link the distribution
libprotobuf, which is built against libstdc++, and therefore
compile the library’s C++20 compatibility path rather than the
reflection path: on that path the members are declared by hand,
so enum and nested-message fields carry their proper types. The
reflection path synthesizes those two as int (Section V), and
the nested and enum cases below are consequently evidence
for the compatibility path only. The wire engine is shared by
both paths; the type mapping is not. For the exercised cases,
messages serialized by Google’s SerializeToString()
decode through ctpb::decode<T>() across scalars, Zigzag
integers, strings, enums, nested messages, bytes fields, and
packed repeated scalars. In the reverse direction, buffers
produced by ctpb::encode() parse through Google’s
ParseFromArray(), with wire tags, varints, and length
delimiters accepted by the reference parser. Packed repeated
fields and bytes are included explicitly because both differ
from the singular scalar path.
