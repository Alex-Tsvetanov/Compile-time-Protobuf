# Checksum manifest, backfilled 2026-09-06

This file adds to the record and changes nothing already in it.

Every entry is the **sha256 of the committed blob**, not of a working-tree file, so this
manifest describes what the repository contains rather than what happens to be on one disk.
It was generated by reading each file back out of git.

## Why a record set needs one

Without a per-file checksum list, a set's completeness is an assertion rather than a check,
and the usual instrument for checking it — `git status` — **cannot see an ignored file**, so
it can never report that a record is missing. That is not hypothetical here: on 6 September
2026 three record sets in this corpus were found to be missing files that `git status` had
reported clean for days, because LaTeX build rules in `.gitignore` were matching measurement
output. 211 logs in `paper-io-portability`, a `build.log` cited by name in a committed README
in `paper-quic-cid-routing`, and four raw `.out` files carrying the evidence for a result.

The `.out` case is the one that shows what a manifest buys: the record published a manifest
of eleven files while the tree held seven, and the discrepancy was visible immediately. The
other two went unnoticed for days, and had been detectable only by someone thinking to look.
